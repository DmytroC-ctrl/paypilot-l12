# ADR-002: ранер збирає словник оракулів, assertion лише читає його

Status: accepted

Context
  Спільна перевірка кейса JNT-026 потребує кількох джерел правди: очікуване рушія, результат інструмента
  з трейсу, рядок клієнта й рядки спорів зі стану стенду. У L03–L09 assertion отримував один результат,
  а гілка `state_row` у `runner._apply` сама ходить у `stand.state()`: HTTP усередині перевірки.
  Assertion engine, який знає про стенд, не можна перевірити без стенду.

Decision
  Ми додаємо крок `collect_oracles(stand, case, run)` у ранері: він повертає словник з ключами
  `engine:disputes`, `tool:check_dispute_eligibility`, `state:customers`, `state:disputes`.
  `assert_case(case, answer, oracles)` і `joint_checks(oracles)` читають лише цей словник і не отримують `stand`.

Consequences
  + Перевірку тестують без мережі: тести `step3` і `step5` використовують фальшивий стенд.
  + Нове джерело правди — один новий ключ у словнику, assertion не змінюється.
  − Ранер мусить знати, які оракули потрібні кейсу: `collect_oracles` зараз зашитий під ключі спорів,
    поле `additional_metadata.oracles` у кейсі поки що не читається.
  − Збираються всі оракули, навіть якщо перевірка впаде на першому: зайві запити до стенду.
  Переглянемо, якщо з'явиться другий спільний кейс з іншими ключами: тоді збір має піти за `metadata.oracles`.

Alternatives
  Assertion сам звертається до стенду (як `state_row` у L09): простіше, але перевірка не ізольована.
  Передавати `stand` у `assert_case`: ті самі проблеми, лише з іншою сигнатурою.
